1. 누가 요청하고 응답할까?

클라이언트는 요청을 보내는 프로그램이고, 웹서버는 웹 요청을 받아 응답하는 프로그램이에요.

curl은 터미널에서 웹 요청을 보낼 수 있는 도구예요. 브라우저 대신 요청을 보내고, 받은 내용을 바로 확인할 수 있어요. 이번 실습에서는 curl이 요청을 보내고, 우리가 만들 C 웹서버가 hello를 돌려줍니다.

IP 주소와 포트 (IP = Internet Protocol)
IP 주소는 접속할 곳을 나타내고, 포트는 그곳에서 어느 서비스에 연결할지 구분해요. 127.0.0.1은 내 컴퓨터, 8080은 실습 서버가 사용할 포트예요.
DNS (Domain Name System)
example.com 같은 이름을 접속에 쓸 IP 주소로 알아내는 데 쓰여요. 실습 주소는 IP를 직접 쓰기 때문에 이름 조회 없이 연결할 수 있어요.
TCP (Transmission Control Protocol)
두 프로그램이 연결을 맺고 순서 있는 바이트를 주고받는 데 쓰는 통신 규칙이에요. TCP 연결을 맺는 SYN → SYN-ACK → ACK 과정을 3-way handshake라고 불러요. SYN(Synchronize)은 순번을 맞추자는 신호, ACK(Acknowledgment)는 받았음을 확인하는 신호예요.
HTTP (Hypertext Transfer Protocol)
웹 요청과 응답의 형식과 의미를 정한 규칙이에요. GET /은 /의 내용을 요청하고, 200 OK는 성공을 알려줘요. 이번 실습에서는 HTTP 메시지를 TCP 연결 위에서 보냅니다.
소켓과 fd (fd = file descriptor)
소켓은 운영체제가 관리하는 통신의 끝점이에요. fd(파일 디스크립터)는 프로그램이 열린 소켓이나 파일을 지정할 때 쓰는 정수예요. 01의 connfd는 연결을, 03의 filefd는 파일을 가리키는 번호예요.
listenfd와 connfd
둘 다 코드에서 붙이는 변수 이름이에요. listenfd(listening file descriptor)에는 연결을 기다리는 소켓의 fd를, connfd(connected file descriptor)에는 받아들인 연결에서 통신할 소켓의 fd를 담아요.
WSL (Windows Subsystem for Linux)
Windows에서 Linux를 실행할 수 있게 해 주는 기능이에요. Ubuntu(우분투)는 이번 실습에서 WSL로 실행하는 Linux 운영체제이고, 터미널은 그 Ubuntu에 명령을 입력하는 창이에요.
POSIX (Portable Operating System Interface)
프로그램이 운영체제 기능을 이용하는 방법을 정한 표준이에요. 여러 운영체제에서 같은 방식으로 코드를 작성할 수 있도록 함수의 이름과 사용법을 정합니다. 이번 과제의 socket(), bind(), listen(), accept()가 그 예이고, WSL의 Ubuntu 환경에서 이 함수들을 호출해 웹서버를 만들어요.
BSD 소켓 (BSD = Berkeley Software Distribution)
버클리에서 개발한 UNIX 계열의 BSD에서 유래한 소켓 사용 방식이에요. 우리가 socket()으로 소켓을 열고 bind(), listen(), accept()를 호출하는 흐름이 이 방식에 해당해요. 이 기본 함수들은 POSIX에도 표준화돼 있어서 Ubuntu에서도 사용할 수 있어요.

코드가 기다린다는 뜻

블로킹은 함수가 결과를 낼 수 있을 때까지 호출한 코드가 그 자리에서 기다리는 방식이에요. accept()는 새 연결을, recv()(receive, 데이터 받기)는 이미 받은 연결의 데이터를 기다려요. 04에서 이 차이를 두 클라이언트로 관찰해요.

주소와 포트를 지정하는 이유

bind()는 서버가 사용할 로컬 주소와 포트를 소켓에 지정해요. 같은 주소와 포트에서 이미 서버가 듣고 있다면 실패할 수 있어요. SO_REUSEADDR(socket option · reuse address)는 서버를 재시작할 때 이전 연결 상태가 주소 재사용에 영향을 주는 경우에 도움이 되는 옵션이에요.

요청 한 건의 흐름

  1. socket → bind → listen으로 서버가 접속을 받을 준비를 하고, accept()로 기다립니다.
  2. 클라이언트가 TCP 연결을 열면 accept()는 연결 소켓의 번호인 connfd를 줍니다.
  3. recv()로 HTTP 요청을 읽고 send()로 HTTP 응답을 보냅니다.
  4. 이번 실습에서는 응답 후 connfd를 닫습니다. listenfd로 다음 연결을 받을 수 있어요.

3. 실제로 오가는 HTTP 메시지

아래에서 \r\n은 실제로 전송하는 줄바꿈 2바이트를 표시한 거예요. 이 두 문자를 합쳐 CRLF라고 해요. CR(Carriage Return)은 \r, LF(Line Feed)는 \n이에요. 시작 줄과 헤더 줄은 각각 CRLF로 끝나고, 마지막에는 CRLF 하나를 더 보내 빈 줄을 만듭니다.

curl이 보내는 요청 · 일부 헤더만 표시

GET / HTTP/1.1\r\n
Host: 127.0.0.1:8080\r\n
\r\n

서버가 돌려주는 응답

HTTP/1.1 200 OK\r\n
Content-Type: text/plain\r\n
Content-Length: 5\r\n
Connection: close\r\n
\r\n
hello

위 예시는 읽기 쉽게 화면에서 줄을 나눴어요. 아래처럼 마지막 헤더부터 이어 쓰면 헤더 줄 끝의 \r\n과 빈 줄의 \r\n이 바로 붙어 있는 게 보여요. 화면에서 나눈 줄은 전송 바이트에 추가되지 않아요.

요청 끝    Host: 127.0.0.1:8080\r\n\r\n
응답 끝    Connection: close\r\n\r\nhello

이 GET 요청은 두 번째 \r\n에서 끝나고, 응답은 그 바로 뒤에 본문 hello가 시작돼요.

Content-Length는 이 메시지의 본문 바이트 수예요. hello는 5바이트이고, 본문 끝에 CRLF까지 보내서 hello\r\n으로 만들면 7바이트예요. curl -w '\n'처럼 터미널 출력에만 줄바꿈을 붙이면 서버가 보낸 본문 길이는 그대로예요. TCP는 바이트를 순서대로 전달하고, 01에서 여러 번 읽어 HTTP 헤더 끝을 찾는 방법을 봅니다.

2. 연결 소켓으로 요청 읽고 응답하기

    
accept(listenfd, …)는 연결 하나를 받아 connfd를 줘요. 이제 그 connfd를 아래 함수에 넘겨서 요청과 응답을 주고받습니다.

    
    
      
  1. recv() (receive, 받다) · 연결된 소켓에서 상대가 보낸 바이트를 읽는 함수예요. 서버는 recv(connfd, …)로 클라이언트가 보낸 데이터를 읽어 버퍼(데이터를 잠시 담아 두는 메모리)에 모아요. 한 번의 호출에서는 헤더 일부만 읽을 수도 있어요. 그래서 서버 코드는 헤더 끝 \r\n\r\n을 찾을 때까지 다시 읽어요. 읽는 크기에 상한을 두고, 헤더가 완성되기 전에 상대가 연결을 닫거나 읽기에 실패하면 해당 연결을 정리합니다.
    2. 
      
  2. send() · 응답 보내기. 상태 줄 HTTP/1.1 200 OK, 헤더, 빈 줄, 본문 hello를 보내요. Content-Length: 5는 본문 길이예요. send()가 일부 바이트만 보냈다면 보낸 양만큼 위치를 옮겨 나머지를 보내요.

3. 두 터미널에서 확인하기

    
첫 번째 WSL 터미널 · 서버에서 코드를 빌드하고 실행해요. Listening…이 나오면 서버가 접속을 기다리는 상태예요.

/tmp/webserver-step1

    
두 번째 WSL 터미널 · 클라이언트에서 curl을 실행해요.

응답 코드를 붙인 뒤에는 서버를 한 번만 켜 둔 상태에서 curl을 연달아 두 번 실행해요. 두 번 모두 < HTTP/1.1 200 OK와 hello가 오면, 서버가 두 연결을 이어서 처리한 거예요.

2. 빈 줄과 본문 길이는 각각 어디에 쓰일까?

    
요청 줄 아래에는 이름: 값 형태의 HTTP 헤더가 와요. Host에는 요청 대상의 호스트와 필요하면 포트가 들어가고, Content-Length는 이 메시지의 본문 바이트 수를 알려줘요. Connection: close는 응답 뒤에 이 연결을 닫겠다는 뜻이에요.

    
요청과 응답의 헤더는 각각 따로 읽어요. 서버가 받은 GET에 본문이 없으면 서버 로그에 Content-Length=0이라고 나올 수 있어요. 같은 요청에 서버가 hello로 응답하면, curl이 받은 응답의 Content-Length: 5와 함께 보여요.

    

      
\r\n\r\n · 본문은 어디에서 시작할까?
마지막 헤더 줄 끝과 그 뒤의 빈 줄을 나타내요. 이 자리를 찾으면 본문이 시작되는 위치를 알 수 있어요.

      
Content-Length: 6 · 얼마나 읽을까?
이 예시의 본문은 6바이트예요. 빈 줄 뒤에 이미 받은 바이트도 포함해서 본문 길이 6을 채울 때까지 읽어요.

3. 파일 종류와 길이 알려주기

    
Content-Type은 응답 본문을 어떻게 해석할지 알려줘요. text/html이나 image/png처럼 정해진 형식 이름을 미디어 타입 또는 MIME(Multipurpose Internet Mail Extensions) 타입이라고 해요.

    
타입 이름은 표준에 등록돼 있고, 파일에 어떤 타입을 붙일지는 서버 코드가 결정해요. 우리 서버의 static_content_type()은 파일 이름 끝의 확장자를 보고 아래 값을 골라요. 모르는 확장자에는 일반 바이너리 데이터라는 뜻의 application/octet-stream을 사용해요.

    
예를 들어 logo.png의 Content-Type: image/png는 PNG로 해석하라는 안내이고, Content-Length: 141은 본문이 141바이트라는 숫자예요. 실제 본문에는 파일의 원래 바이트를 넣어요.

fork() 직후에는 부모와 자식이 같은 연결을 가리키는 connfd를 각각 가지고 있어요. 부모는 자기 쪽 connfd를 닫고 accept()로 돌아가요. 자식은 새 연결을 받는 listenfd를 닫고, 자기 connfd로 요청을 처리해요. 자식이 끝나면 부모가 SIGCHLD를 받고 waitpid()로 정리해요.

    
두 번째 구현 · pthread 스레드 풀 확인하기

터미널 1. 앞에서 켠 서버를 Ctrl+C로 끈 뒤 아래 세 줄을 실행해요. -pthread는 POSIX 스레드를 쓰는 코드를 컴파일하고 연결하는 GCC 옵션이에요.

gcc -std=c17 -Wall -Wextra -pthread server.c -o /tmp/webserver-pthread
/tmp/webserver-pthread --pthread

    
    
      
  1. 작업 스레드가 하나 비어 있을 때. 3번의 Python과 curl 명령을 사용해요. A를 열고 Enter를 누르기 전에 B가 200 OK와 hello를 받는지 확인해요.
    2. 
      
  2. 작업 스레드가 둘 다 사용 중일 때. A를 계속 열어 두고, 새 Ubuntu 터미널에서 같은 Python 명령을 한 번 더 실행해 두 번째 연결을 열어요. 둘 다 Enter를 누르지 않은 상태에서 B의 curl을 실행하면 시간 초과가 나요. Python 연결 하나를 닫고 B를 다시 실행하면 응답을 받아요.
    3.

터미널 1. 앞에서 켠 서버를 Ctrl+C로 끄고 아래 세 줄을 실행해요.

마지막 구현 · 연결이 열린 채 서버 종료하기

    • 
      
  • pthread. 대기열의 연결을 닫고, 처리 중인 소켓에 shutdown()을 호출해 작업 스레드를 깨워요. pthread_join()은 스레드가 끝날 때까지 기다리는 함수예요.
    • 
      
  • poll(). poll()이 기다리는 목록에 종료 알림용 파이프도 넣어 둬요. 신호 처리 함수가 파이프에 알림을 쓰면 이벤트 루프가 깨어나 소켓과 열어 둔 파일을 닫아요.

직접 확인하기. 위 명령으로 서버를 다시 빌드하고 켜세요. Python으로 A의 연결을 연 뒤 A에서는 Enter를 누르지 말고, 서버 터미널에서 Ctrl+C를 누르세요. 서버에 Server stopped.가 나오고 명령 프롬프트로 돌아오면 정리를 끝낸 거예요. Python 창에 입력 안내가 남아 있을 수 있어요. 그 안내는 Python이 서버 응답을 읽는 대신 키보드 입력을 기다리는 것이므로, Enter를 눌러 Python도 끝내면 돼요.

    
SIGTERM으로도 확인하려면 서버 시작 로그의 pid=… 숫자를 읽고, 다른 Ubuntu 터미널에서 kill -TERM 숫자를 실행해요. SIGPIPE는 별개로, 이미 끊긴 연결에 쓰다가 서버 전체가 종료되는 것을 막기 위해 무시해요.

1. 프록시란 무엇일까?

    
프록시(Proxy)는 중간에서 요청을 받아 목적지로 전달하고, 받은 응답을 요청한 쪽에 돌려주는 서버예요. 포워드와 리버스 모두 요청과 응답을 중계해요. 차이는 누구를 대신해 목적지에 연결하느냐예요.

    

      

        
Forward Proxy · 클라이언트 쪽 대리인

        
예를 들어 회사 PC가 외부 사이트에 접속할 때 회사 프록시를 쓰도록 설정해요. PC가 방문할 사이트를 정하고, 회사 프록시가 그 사이트에 대신 연결해 응답을 PC에 돌려줘요.

        
회사 PC → 회사 프록시 → PC가 지정한 외부 사이트

      

      

        
Reverse Proxy · 서비스 쪽 대리인

        
예를 들어 사용자는 쇼핑몰 주소로만 접속해요. 쇼핑몰 앞단의 프록시가 요청 경로를 보고, 주문 요청이면 뒤쪽 주문 서버에 맡긴 뒤 응답을 사용자에게 돌려줘요.

        
사용자 → 쇼핑몰 앞단 프록시 → 서비스가 정한 주문 서버

      

    

    
원 서버(Origin Server)는 요청한 페이지나 데이터를 제공하는 서버예요. 우리 포워드 예시에서는 curl이 지정한 목적지예요. 백엔드 서버는 앞단 서버의 뒤에서 요청을 맡는 서버예요. 쇼핑몰의 주문 백엔드가 주문 응답을 만든다면, 이 요청의 실제 응답을 제공하는 곳이기도 해요.

    
과제의 필수 기준은 두 방식 중 최소 하나예요. 우리 실습에서는 리버스 프록시를 먼저 구현하고, 이어서 포워드 프록시도 구현해요. 리버스에서는 C 서버에 정해 둔 규칙으로 목적지를 고르고, 포워드에서는 클라이언트가 요청에 적어 준 목적지에 연결해요.

4. 첫 구현 · 리버스 프록시를 WSL에서 켜 보기

    
이번에 실행할 경로는 curl → 리버스 프록시(8080) → 백엔드(8001)예요. 아래에서 부르는 ‘터미널 1·2·3’은 명령을 입력할 창을 구분하는 이름이에요. Ubuntu 창은 어느 것을 써도 돼요. 두 C 서버의 역할은 같은 /tmp/webserver-proxy를 켤 때 지정한 포트와 --reverse 설정으로 정해져요.

    
터미널 1 · 백엔드. 아래 명령을 한 줄씩 실행해요. 임시 폴더에 api/hello 파일을 만든 뒤, C 서버를 8001에서 켜요. 이 서버가 backend hello를 보내는 쪽이에요.

    
cd "/mnt/d/jsy/Krafton Jungle/13week"
gcc -std=c17 -Wall -Wextra -pthread server.c -o /tmp/webserver-proxy
backend_root=$(mktemp -d)
mkdir -p "$backend_root/api"
printf '%s' 'backend hello' > "$backend_root/api/hello"
/tmp/webserver-proxy --port 8001 --root "$backend_root"

    
터미널 2 · 리버스 프록시. 04에서 켠 서버가 8080을 사용 중이면 먼저 그 서버를 Ctrl+C로 끄세요. --reverse /api/=8001은 /api/로 시작하는 요청을 8001에 보내라는 설정이에요. 여러 규칙이 맞으면 더 긴 경로가 우선이에요.

    
cd "/mnt/d/jsy/Krafton Jungle/13week"
/tmp/webserver-proxy --pthread --port 8080 --root public --reverse /api/=8001

    
터미널 3 · curl. 두 명령 모두 8080에 접속해요. 첫 번째는 백엔드의 backend hello를 받고, 두 번째는 프록시가 직접 읽은 public/index.html을 받아요. 첫 번째 요청은 백엔드 터미널에도 GET /api/hello가 찍혀요.

    
curl --http1.1 -i -w '\n' http://127.0.0.1:8080/api/hello
curl --http1.1 -i -w '\n' http://127.0.0.1:8080/index.html

    
실패도 한 번 확인해요. 백엔드 터미널에서 Ctrl+C를 눌러 백엔드만 끄고 첫 번째 요청을 다시 보내세요. 프록시가 연결에 실패하면 502 Bad Gateway를 돌려줘요. 연결했지만 2초 안에 응답을 받지 못하면 504 Gateway Timeout을 돌려줘요.

    
현재 구현은 HTTP GET과 POST를 중계하고, 백엔드 응답의 상태·Content-Type·본문을 전달해요. 백엔드 응답은 Content-Length 또는 연결 종료로 끝을 알리고, 본문은 최대 1 MiB예요. --poll과 함께 실행하면 백엔드 응답을 받는 동안 이벤트 루프가 기다릴 수 있으므로, 이 실습은 --pthread로 진행해요.

    

      왜 프록시 실습은 --pthread로 실행할까?
      
느린 백엔드가 /api/hello의 응답을 보류하는 동안 /index.html을 요청했어요. WSL에서 --fork와 --pthread는 HTML을 먼저 보냈고, 현재 --poll 구현은 백엔드 응답이 돌아올 때까지 HTML도 기다렸어요.

      
    
        
  • --pthread. 워커 하나가 백엔드를 기다리는 동안 비어 있는 다른 워커가 정적 파일을 보내요. 같은 프로세스 안에서 라운드 로빈 순번과 캐시를 공유할 수 있어요. 여러 워커가 함께 바꾸는 값은 잠금으로 보호해야 해요.
    • 
        
  • --fork. 자식 프로세스가 연결을 따로 처리하므로 느린 백엔드를 기다리는 작업도 분리돼요. 요청마다 자식이 가진 메모리가 따로라 전체 요청의 순번이나 캐시를 공유하려면 별도의 공유 방식이 필요해요.
    • 
        
  • --poll. 클라이언트 소켓 여러 개의 준비 상태를 확인해요. 현재 백엔드 중계는 응답을 기다린 뒤 반환하는 함수라 같은 루프의 다른 요청도 기다려요. 백엔드 소켓까지 같은 루프에서 관리하려면 연결·송신·수신 상태를 나눠야 해요.

      심화 · 요청 경로가 길 때와 본문이 클 때
      
    
        
  • GET과 POST의 요청 줄에서 경로나 URL이 4,096바이트를 넘으면 414 URI Too Long을 보내요. 받는 중에도 그 한도를 넘긴 걸 확인하면 더 기다리지 않아요.
    • 
        
  • 헤더의 Content-Length가 본문 한도인 8,192바이트를 넘으면 413 Content Too Large를 보내요.
    • 
      

      
WSL의 pthread와 poll 모드에서 4,096바이트 요청 경로는 길이 검사에 통과했고, 4,097바이트와 8,307바이트는 414가 나왔어요. 그 뒤 새 정상 요청에는 200 OK가 돌아왔어요. 두 크기 제한은 실습 서버가 정한 값이에요.

    

    

      심화 · 불완전한 요청과 미지원 요청의 실제 결과
      
    
        
  • 헤더나 본문을 다 보내기 전에 클라이언트가 송신을 끝내면 해당 연결을 HTTP 응답 없이 닫았어요.
    • 
        
  • 요청 줄에서 HTTP 버전이 빠진 경우는 400 Bad Request, 지원하지 않는 PUT 메서드는 501 Not Implemented, 지원하지 않는 HTTP/9.9 버전은 505 HTTP Version Not Supported가 나왔어요.
    • 
        
  • 다음 정상 요청은 200 OK였어요. 헤더 끊김과 요청 줄·메서드·버전 결과는 pthread와 poll에서 각각 확인했어요.
    • 
      

    

    

      심화 · 프록시 메모리 검사 결과
      
별도 WSL 환경에서 포워드와 리버스 프록시를 -fsanitize=address,leak로 빌드한 서버로 실행했어요. 정상 요청은 두 프록시를 거쳐 200 OK와 backend hello를 받았고, 백엔드를 끈 뒤에는 502가 왔어요. 리버스 프록시에 직접 요청했을 때 백엔드가 응답하지 않으면 504가 왔고, 그다음 정상 요청은 다시 200이었어요.

      
두 프록시 모두 정상 종료했고, 이번 요청 처리와 종료 과정에서 메모리 접근 오류나 누수 보고는 없었어요.

    현재 실습 · make로 서버 빌드하기
    
    
    과제는 다른 사람도 같은 방식으로 C 서버를 빌드할 수 있도록 빌드 파일을 요구해요. Makefile은 빌드 방법을 적은 파일이고, make는 그 파일을 읽어 필요한 명령을 실행하는 도구예요. webserver: server.c는 webserver 실행 파일을 만들려면 server.c가 필요하다는 뜻이에요. 실행 파일이 없거나 소스가 더 최근에 바뀌면 아래 줄의 gcc 명령으로 빌드해요.
    
    
    
      
    makeMakefile을 읽고 필요하면 gcc로 실행 파일을 만듦
    →
      
    만들어진 서버 파일 실행서버가 포트를 열고 Listening을 출력
    →
      
    다른 터미널에서 curl해당 포트에 이미 실행 중인 서버에 요청
    
    
    
    
    지금까지처럼 대상 포트에서 서버가 실행 중이어야 응답이 와요. 디스크에 실행 파일이 생긴 뒤 그 파일을 직접 실행해야 서버가 켜져요. 같은 포트에 이전 서버가 실행 중이면, 새로 빌드한 직후의 curl에도 이전 서버가 응답할 수 있어요.
    
    
    실제로 적어 둔 Makefile
    
    
    CC = gcc
CFLAGS ?= -std=c17 -Wall -Wextra

webserver: server.c Makefile
	$(CC) $(CPPFLAGS) $(CFLAGS) -pthread $(LDFLAGS) -o $@ $< $(LDLIBS)

.PHONY: clean
clean:
	$(RM) webserver
    
    
      
      
    • CC = gcc는 컴파일러를 골라요. CFLAGS ?=는 CFLAGS가 정의되지 않았을 때만 오른쪽의 기본 옵션을 써요.
      • 
      
    • webserver: server.c Makefile은 만들 파일과 빌드에 필요한 파일을 적은 규칙이에요. 탭으로 들여쓴 다음 줄이 실행할 명령이에요. $@는 만들 파일인 webserver, $<는 첫 입력인 server.c예요. 별도 옵션을 주지 않으면 CPPFLAGS, LDFLAGS, LDLIBS는 비어 있어요.
      • 
      
    • .PHONY: clean은 clean을 파일 이름 대신 작업 이름으로 취급하라는 뜻이에요. make clean을 하면 GNU Make의 기본 $(RM)이 rm -f로 풀려, 생성한 webserver 파일을 삭제해요.
      • 
    
    
    
    기본 설정에서 실행하는 명령

    라운드 로빈으로 백엔드 고르기
    
    
    1. 로드 밸런싱과 라운드 로빈부터 이해하기
    
    
    로드 밸런싱(load balancing)은 같은 일을 할 수 있는 여러 서버에 요청을 나눠 보내는 일이에요. 라운드 로빈(round robin)은 서버마다 차례로 한 번씩 보내고, 마지막 서버를 고른 뒤 첫 번째 서버로 돌아가는 방법이에요.
    
    
    경로 라우팅과 라운드 로빈은 무엇을 각각 고를까?
    
    
    curl은 8080에 접속해서 GET /api/hello를 보내요. 8080이 가지고 있는 설정에 /api/ → 8001, 8002라고 적혀 있다고 가정해 볼게요. 두 번호는 같은 /api/ 요청을 처리할 수 있는 백엔드의 포트예요.
    
    
    
    
    2. 이번 확장에서 pthread를 쓰는 이유
    
    
    실습의 8080은 --pthread로 실행해요. 워커는 요청을 맡아 처리하는 스레드예요. 워커 두 개가 같은 프로세스에 있어서, 각 경로 규칙의 ‘다음 차례’를 같은 곳에서 읽고 바꿀 수 있어요.
    
    
      
      
    1. 워커 하나가 잠깐 잠금을 잡고 현재 차례인 8001을 고른 뒤, 다음 차례를 8002로 바꿔요. 잠금은 두 워커가 이 작업을 동시에 하지 못하게 해요.
      2. 
      
    2. 워커가 잠금을 풀고 나서 8001에 연결해 응답을 기다려요. 그동안 다른 워커도 잠금을 잡아 8002를 고를 수 있어요.
      3. 
    
    
    
      
      
    • fork()로 한다면 자식 프로세스마다 메모리가 따로라 순번을 함께 쓰는 방법을 추가해야 해요. 느린 백엔드를 기다리는 요청과 다른 요청을 분리하는 데는 이미 성공했어요.
      • 
      
    • poll()로 한다면 이벤트 루프 하나가 순번을 관리하니 순번 자체에는 스레드 잠금이 필요 없어요. 지금은 그 루프가 백엔드 응답도 기다려서 다른 요청이 밀려요. 백엔드 연결까지 논블로킹으로 관리하면 그 대기를 줄일 수 있어요.
      • 
    
    
    
    복습 · 첫 요청이 아직 8001의 응답을 기다리는 중이면, 둘째 요청은 어디로 갈까요?
    빈 워커가 둘째 요청을 맡으면 8002로 가요. 첫 워커가 8001을 골랐을 때 이미 다음 차례를 8002로 바꿔 두었기 때문이에요.
    
    
    3. 완료 · WSL에서 실제 라운드 로빈 확인하기
    
    
    --reverse /api/=8001,8002처럼 쉼표로 후보를 적어요. 다른 경로에 별도의 --reverse 규칙을 추가하면 그 경로의 차례는 따로 움직여요. 기존의 --reverse /api/=8001도 쓸 수 있어요.

    같은 요청을 두 번 보내 어디까지 가는지 보기
    
    
  
    
  
    
    
    실제 서버의 --cache로 확인하기
    
    
    프록시에 --cache를 붙이면, 원 서버가 Cache-Control: public, max-age=...나 s-maxage로 재사용을 허용한 공개 GET의 200 응답을 메모리에 보관해요. 최대 16개, 응답 본문은 64 KiB까지, 보관 시간은 최대 60초예요. 캐시에서 돌려준 응답에는 Age가 붙고, 프록시 터미널에서는 Cache HIT를 확인할 수 있어요.
    
    
    인증이나 쿠키가 있는 요청과 private, no-store, Set-Cookie, Vary가 있는 응답은 공유 캐시에 보관하지 않아요. 리버스 프록시에서 캐시 적중 시에는 백엔드 선택 단계까지 가지 않으므로 라운드 로빈 차례도 넘어가지 않아요.

    실제로 사용한 POSIX 헤더
    
    
    socket.h는 파일 이름이고, sys/socket.h는 헤더를 찾을 때 쓰는 경로예요. 실제 server.c 윗부분에도 아래 줄이 있어요.
    
    
    #include <sys/socket.h>   /* 소켓 함수와 자료형 선언을 가져오기 */
    
    
    컴파일러는 이 헤더에서 socket()의 이름, 인자와 반환값의 타입 등을 알아요. #include는 빌드할 때 헤더를 읽는 단계예요. 실제 서버가 실행되는 동안에는 아래쪽의 socket() 호출이 소켓을 만들어요. POSIX(Portable Operating System Interface)는 이런 운영체제 기능을 프로그램에서 쓰는 방법을 정한 표준이에요.
    
    
    지금 공부할 범위. 헤더 파일 목록을 외울 필요는 없어요. 먼저 socket()·accept()·recv()가 연결 과정에서 무엇을 하는지 말할 수 있으면 돼요. 다른 함수나 타입은 코드를 같이 볼 때 아래 표에서 찾아보세요.
    
    
    
      
    <sys/socket.h> · 연결과 통신
    socket(), bind(), listen(), accept(), recv(), send().
    
      
    <netinet/in.h> · IP 주소와 포트
    IPv4 주소와 포트를 함께 담는 sockaddr_in 같은 자료형과 상수.
    
      
    <unistd.h> · 파일과 프로세스
    read()로 읽고, close()로 닫고, fork()로 자식 프로세스를 만들어요.
    
      
    <pthread.h> · 스레드와 잠금
    스레드를 시작하고, 종료를 기다리고, 두 워커가 함께 쓰는 값을 잠금으로 보호해요.
    
      
    <poll.h> · <fcntl.h>
    여러 fd의 준비 상태를 확인하고, 소켓에 O_NONBLOCK 옵션을 설정해요.
    
      
    <signal.h> · <sys/wait.h>
    시그널을 받아 처리하고, waitpid()로 종료한 자식 프로세스를 수거해요.
    
    
    
    
    fd(file descriptor)는 열린 파일이나 소켓을 가리키는 정수 번호예요. 예를 들어 connfd=4는 받아들인 연결에 4라는 번호로 접근한다는 뜻이에요.
    
  
    

  
    
    
    소켓 대기와 HTTP 메시지 경계
    
    
    TCP는 두 프로그램 사이에 데이터를 주고받을 연결을 만들어요. HTTP는 그 연결로 보낼 요청의 형식을 정해요.
    
    
    연결이 됐다는 것과 요청을 다 받았다는 것
    
    
    curl은 POST /echo 요청을 실제로 보낼 때 요청 줄, 헤더, jungle을 바이트로 보내요. 서버에서 HTTP 바이트를 읽는다는 말은 recv()로 그 바이트를 메모리에 가져온다는 뜻이에요.
    
    
    
    같은 8080 포트에 다시 bind()할 때
    
    
    
    블로킹과 논블로킹 · A가 연결만 열어 두면?
    
    
    
      
    블로킹 recv(A)
    A가 아직 아무 데이터도 보내지 않았어요. 호출한 워커는 그 함수 안에서 데이터가 오거나 연결이 끝날 때까지 기다려요. 스레드 풀에 빈 워커가 있으면 그 워커가 B를 맡을 수 있어요.
    
      
    논블로킹 recv(A)
    읽을 게 없으면 즉시 -1과 errno=EAGAIN 등을 돌려줘요. 지금은 읽을 게 없으니 나중에 다시 보라는 뜻이에요. 이 실행 흐름은 B를 살펴볼 수 있어요.
    
    
    
    
    
    
      recv()가 돌려주는 숫자도 확인하기
      
      
        
    • 양수 · 이번 호출에서 읽은 바이트 수예요. 요청 일부만 읽어도 양수가 나올 수 있어요.
      • 
        
    • 0 · 이 TCP 연결에서 상대가 송신을 끝냈고, 읽을 데이터도 다 읽은 상태예요.
      • 
        
    • -1과 EAGAIN 또는 EWOULDBLOCK · 논블로킹 소켓에 지금 읽을 게 없어요. 준비됐을 때 다시 읽어요.
      • 
      
    
    
    
    
    
    accept()는 새 연결을 받아들이고, recv()는 받아들인 연결에서 데이터를 읽어요.

    POST /echo HTTP/1.1\r\n
Host: 127.0.0.1:8090\r\n
Content-Length: 6\r\n\r\n
jungle
    
    
      
      
    1. 요청 줄 · 첫 \r\n. 첫 줄을 공백으로 나눠 POST, /echo, HTTP/1.1을 읽어요.
      2. 
      
    2. 헤더 구간 · \r\n\r\n. 마지막 헤더 줄을 끝내는 줄바꿈과, 그 뒤 빈 줄의 줄바꿈을 함께 찾으면 본문이 시작할 위치가 나와요.
      3. 
      
    3. 본문 · Content-Length 바이트. 이 값이 6이면 6바이트를 채워야 해요. 헤더와 함께 ju가 왔다면 이미 2바이트를 받았으니 4바이트만 더 읽어요.
      4. 
    
    
    
    한 번의 recv()에 요청 일부나 헤더와 본문 일부가 함께 들어올 수 있어요. 그래서 서버는 받은 바이트를 모아 경계를 찾아요.
    
    
    
      
    Content-Length 방식
    보내기 전에 본문의 길이를 헤더에 써요. 받는 쪽은 정확히 그만큼 읽어서 연결이 열려 있어도 끝을 알 수 있어요.
    
      
    청크 전송
    전체 길이를 미리 모를 때 본문을 덩어리로 나눠 보낼 수 있어요. 받는 쪽은 각 덩어리의 길이와 끝을 읽는 규칙이 추가로 필요해요. 우리 요청 본문 실습은 Content-Length 방식이에요.

    fork() · 연결별 자식 프로세스
    메모리 공간이 분리돼 작업을 나누기 쉬워요. 연결마다 프로세스를 만들고, 종료한 자식을 수거하는 비용이 들어요.
    
      
    pthread · 미리 만든 워커
    워커를 재사용하고 라운드 로빈 순번과 캐시를 함께 쓸 수 있어요. 공유 값에는 잠금이 필요하고, 지금 워커 두 개가 모두 기다리면 다음 작업도 대기해요.
    
      
    poll() · 이벤트 루프 하나
    준비된 연결을 골라 번갈아 처리해요. 연결마다 어디까지 읽고 썼는지 기억해야 해요. 우리 구현은 백엔드에 중계하는 동안 같은 루프도 기다려요.
    
    
    

    
    C10K가 세는 것은 연결 수예요
    
    
      
      
    • 뜻. 서버가 연결 약 1만 개를 동시에 유지하려면 무엇을 고려해야 하는지 묻는 문제예요.
      • 
      
    • 볼 것. 열 수 있는 fd 수, 연결마다 필요한 메모리, 대기 시간 제한, 준비된 연결을 찾는 비용.
      • 
      
    • 우리 실습 수치. poll 모드의 활성 클라이언트 한도는 64개예요. ab 실험은 동시 요청 1개와 8개의 처리량을 비교했어요. 동시 연결 수와 초당 요청 수는 각각 따로 봐요.
      • 
      
    • 현재 결론. 우리는 여러 연결을 같이 처리하는 방법을 구현했어요. C10K는 이 구현으로 달성한 목표가 아니에요. 한도를 늘린다면 소켓 번호와 메모리 한도, 유휴 연결 대기 시간, 백엔드 중계가 이벤트 루프를 멈추게 하는 부분까지 별도로 확인해야 해요.

    메모리와 연결의 수명
    
    
    
      
    응답 메모리 · malloc() → free()
    프록시가 받은 응답을 담을 메모리를 할당해요. 전송 후나 읽기 실패 때 해제하고, 캐시에 저장한 사본은 교체·무효화·종료 때 해제해요.
    
      
    버퍼 오버플로우 · 범위를 넘어 쓰는 오류
    버퍼는 데이터를 담아 두는 메모리 공간이에요. 코드는 남은 공간을 계산해 읽고, 요청 대상 4,096바이트와 본문 8,192바이트를 검사해요. 한도를 넘는 414와 413을 실험으로 확인했어요.
    
      
    클라이언트 연결 · connfd
    6바이트 중 ju만 보내고 송신을 끝내면, 서버가 읽기를 중단하고 해당 연결을 닫아요. 다음 정상 요청은 계속 처리했어요.
    
      
    정적 파일과 백엔드 소켓
    파일을 다 보내거나 중간에 실패하면 파일을 닫아요. 프록시가 원 서버의 응답을 받거나 실패한 뒤에는 백엔드 연결을 닫아요.
    
    
    
    
    시그널별로 무슨 일이 생길까?
    
    
      
      
    • SIGINT · 터미널에서 Ctrl+C. 우리 서버는 새 연결 수락을 멈추고 열린 연결을 정리해요. 기다리던 워커나 자식을 수거하고 Server stopped.를 출력해요.
      • 
      
    • SIGTERM · 일반 종료 요청. 같은 정리 절차를 타요. 두 시그널로 종료 코드 0과 포트 반환을 확인했어요. 처리 중 연결은 닫아 읽기·쓰기 대기를 풀어요.
      • 
      
    • SIGPIPE · 끊긴 연결에 쓸 때 발생할 수 있는 시그널. 서버는 이 시그널을 무시하도록 설정하고 send() 실패를 처리해요. 이전 실습에서 Broken pipe가 나온 뒤에도 다음 요청에 응답했어요.
